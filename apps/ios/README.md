# Safe World — iOS

> **Status:** Phase 2 in progress. App + Safari Content Blocker extension are scaffolded and build;
> Screen Time integration is not started (see [Next steps](#next-steps)).

## Goal

Block scam/malware, gambling, and adult sites on iPhone/iPad, across Safari and (where the OS
allows) system-wide.

## Stack

- **Language / build:** Swift + SwiftUI. The Xcode project is generated from
  [`project.yml`](project.yml) via [XcodeGen](https://github.com/yonaskolb/XcodeGen) — edit
  `project.yml`, not `SafeWorld.xcodeproj` by hand, then re-run `xcodegen generate`.
- **Min iOS:** 16.0.
- **Targets:**
  - `SafeWorld` — the SwiftUI host app (master switch, per-category toggles, custom allow/block
    lists, remote updates, "blocked today" counter).
  - `SafeWorldBlocker` — a Safari Content Blocker app extension.
  - `SafeWorldCore` — a local Swift package (`SafeWorldCore/`), the iOS analogue of
    `packages/core`: category metadata, `Settings`/`DailyStats` types, the `Matcher.decide`
    precedence logic, and the Content Blocker rule-list builder. Pure Foundation, no UIKit —
    shared by both the app and the extension, and unit-testable on macOS with `swift test` (no
    simulator required).

## Blocking approach

Safari on iOS only loads **one** active rule list per Content Blocker extension, unlike Chrome's
`declarativeNetRequest`, which can toggle several static rulesets independently. So instead of one
ruleset per category, `SafeWorldCore.BlockerListBuilder` compiles the user's settings into a
**single combined rule list**, mirroring `Matcher.decide`'s precedence:

1. One `block` trigger per enabled category (bundled domains ∪ any fetched remote domains).
2. One `block` trigger for the user's custom block list.
3. One `ignore-previous-rules` trigger for the user's custom allow list, placed **last** so it
   always wins — matching `decide()`'s "custom allow beats everything" precedence regardless of
   rule order elsewhere in the list.

`if-domain` entries use a `*domain.com` prefix, which Safari matches against the domain and all of
its subdomains — the same semantics as `Matcher.hostMatchesDomain` / `hostInList`.

The host app (not the extension) rebuilds this list on every settings change, writes it as JSON to
a **shared App Group container** (`group.com.safeworld.app`), and calls
`SFContentBlockerManager.reloadContentBlocker` to ask Safari to reload it. The extension's
`ContentBlockerRequestHandler` just hands Safari whatever is in that shared file — it does no
computation of its own, per Apple's constraint that content blocker extensions must respond
quickly. Before the app has ever run, the extension falls back to a default list bundled in its own
resources (all default-enabled categories, generated by `npm run build:ios`).

This gets category toggles, custom allow/block lists, and remote updates all working through a
regular Safari Content Blocker — no special entitlement required. What it does **not** cover is
non-Safari browsers or system-wide blocking; that needs a `NEFilterDataProvider`/`NEDNSProxyProvider`
Network Extension (gated by Apple, typically requires a supervised/MDM context) or Screen Time
(`FamilyControls`) restrictions — both still on the roadmap, see below.

## Reusing shared logic

- `npm run build:ios` copies the per-category domain lists from `packages/core/src/blocklists/`
  into `SafeWorldCore/Sources/SafeWorldCore/Resources/` (read at runtime via `Blocklists.swift`),
  and generates the extension's bundled fallback rule list at
  `SafeWorldBlocker/Resources/blockerList.json`. Run it whenever the core blocklists change.
- Matching precedence follows the spec in `packages/core/src/matcher.ts` (`decide`), reimplemented
  in `SafeWorldCore/Sources/SafeWorldCore/Matcher.swift`. The two are meant to be kept in sync by
  hand (no codegen between TS and Swift); `SafeWorldCore/Tests/SafeWorldCoreTests/MatcherTests.swift`
  mirrors `packages/core/test/matcher.test.ts` case-for-case.

## Building

```bash
brew install xcodegen           # once
npm run build:ios               # regenerate SafeWorldCore resources + default blocker list
cd apps/ios && xcodegen generate # regenerate SafeWorld.xcodeproj from project.yml
open SafeWorld.xcodeproj        # build/run from Xcode (needs a simulator or device + signing team)
```

To just run the platform-agnostic core's tests, no Xcode project or simulator needed:

```bash
cd apps/ios/SafeWorldCore && swift test
```

Building the full app from the command line (e.g. in CI) needs an iOS Simulator platform installed
(`Xcode > Settings > Components`, or `xcodebuild -downloadPlatform iOS`); with one installed:

```bash
xcodebuild -project apps/ios/SafeWorld.xcodeproj -scheme SafeWorld \
  -sdk iphonesimulator -destination 'platform=iOS Simulator,name=<a simulator name>' build
```
